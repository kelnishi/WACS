# Sprint Plan: AOT-Compatible WASI + Generic Host-Binding Source Generation

## Goal

End state: a single `wacs aot foo.wasm -o foo --wasi` produces a self-contained
NativeAOT native binary that runs a WASI Preview 1 wasm module. The same
source-generation infrastructure transparently handles WASI Preview 2 and any
third-party host-binding package that opts in. Interpreter and in-process
transpiler paths are unaffected. The `WACS.WASIp1` NuGet identity is deprecated
in favor of `WACS.WASI.Preview1` with type-forward back-compat.

## Outcome shapes

End-user CLI:

```
wacs aot myapp.wasm -o myapp --wasi          # WASI Preview 1
wacs aot mycomponent.wasm -o myapp --wasip2  # WASI Preview 2
wacs aot myapp.wasm -o myapp --bind GameHost.dll  # custom host bindings
```

End-user csproj (DIY embedding without `wacs aot`):

```xml
<ItemGroup>
  <Reference Include="MyTranspiledApp" HintPath="MyTranspiledApp.dll" />
  <PackageReference Include="WACS.WASI.Preview1" />     <!-- the bindings -->
  <PackageReference Include="WACS.HostBindings.SourceGen" /> <!-- the generator -->
</ItemGroup>
```

The generator emits a `GeneratedHostImports` class implementing
`MyTranspiledApp.IImports`; the embedder constructs
`new Module(new GeneratedHostImports(wasiConfig))`.

Custom host author:

```csharp
public static class MyEngineBindings
{
    [WacsImport("game_engine", "log")]
    public static void Log(WacsHostMemory mem, int strPtr, int strLen) { ... }

    [WacsImport("game_engine", "set_pixel")]
    public static int SetPixel(WacsHostMemory mem, int x, int y, int color) { ... }
}
```

The generator picks these up automatically.

## Scope

**In:** Package rename + type forwarding; ExecContext-free entry points across
WASI Preview 1; `[WacsImport]` attribute + `WacsHostMemory` abstractions
package; Roslyn source generator for `IImports` adapter synthesis; `wacs aot
--wasi` end-to-end; matching annotations on `Wacs.WASI.Preview2`; migration
doc.

**Out:** Unifying `IBindable` with `[WacsImport]` (deferred to a Wacs.Core 1.0
cleanup); WASI Preview 3; `wacs aot` for component-mode wasm beyond Preview 2;
rebuilding the in-process transpiler engine to drop DispatchProxy (could come
for free, but not required by this sprint).

## Architecture

Three new packages, one big refactor, one wiring change in the CLI.

```
                                 used by
                            ┌─────────────────────┐
   WACS.HostBindings        │                     │
   .Abstractions            ▼                     │
   (netstandard2.0)    ┌──────────────────────┐   │
   • [WacsImport]      │ WACS.WASI.Preview1   │   │
   • WacsHostMemory    │  • IBindable + Wasi  │───┘ interpreter (unchanged)
   • WacsHostFault     │  • [WacsImport]-     │
                       │    annotated statics │  ◄── consumer build references
                       │                      │      this for AOT bindings
                       └──────────────────────┘

   WACS.HostBindings        ┌─────────────────────────────┐
   .SourceGen          ─────►  Generated by source gen at │
   (netstandard2.0,         │  consumer build time:       │
    Roslyn analyzer)        │                             │
                            │  class GeneratedHostImports │
                            │      : IImports             │
                            │  { /* delegates to          │
                            │       [WacsImport] statics  │
                            │       discovered in refs */ │
                            │  }                          │
                            └─────────────────────────────┘
```

Old `WACS.WASIp1` NuGet stays as a thin metapackage:

```xml
<PackageReference Include="WACS.WASI.Preview1" Version="0.11.0" />
```

plus a ship-only assembly with `[assembly: TypeForwardedTo(typeof(...))]`
entries so `using Wacs.WASIp1;` keeps resolving without recompilation.

## Phasing

Each phase ends green (existing test suites pass) and produces a reviewable
commit.

### Phase 1 — Rename `Wacs.WASIp1` → `Wacs.WASI.Preview1` (~0.5 day)

- Rename project directory, csproj, `AssemblyName`, `PackageId`,
  `RootNamespace`. Source files keep the same logical structure.
- Move `namespace Wacs.WASIp1` → `namespace Wacs.WASI.Preview1` across all
  files.
- Bump version `0.10.0` → `0.11.0`.
- Create a new `Wacs.WASIp1` deprecated metapackage. CLR's
  `TypeForwardedTo` only redirects same-named types between assemblies,
  it doesn't bridge a namespace rename — so the shim is just a NuGet
  metapackage that pulls in `WACS.WASI.Preview1` transitively. Consumers
  need a one-shot sed to update `using Wacs.WASIp1;` lines (see migration
  doc in Phase 7).
- Update internal references: `Wacs.Console`, `Wacs.Bench.Aot`,
  `Wacs.WASIp1.Test` (rename to `Wacs.WASI.Preview1.Test`), all CLI `using`
  lines.
- Mark old `WACS.WASIp1` package with deprecation note + pointer.

**Verification:** `dotnet test Wacs.WASI.Preview1.Test`, full Spec.Test,
build a sample with `<PackageReference Include="WACS.WASIp1" />` and
confirm it transitively pulls in `WACS.WASI.Preview1`.

**Why no source-level back-compat:** CLR `TypeForwardedTo` only redirects
*same-named* types across assembly boundaries; it has no mechanism for
"these types used to be at namespace X, look there if X.Y isn't found in
the new namespace." The .NET ecosystem's standard pattern for namespace
renames is package-level deprecation + source migration (one sed). We
follow that.

### Phase 2 — `WACS.HostBindings.Abstractions` package (~0.25 day)

Tiny netstandard2.0 assembly. Three public types:

- `[AttributeUsage(AttributeTargets.Method)] WacsImportAttribute(string module, string name)`
- `readonly struct WacsHostMemory` — wraps a `byte[]` (or
  `Span<byte>`/`Memory<byte>`) plus the live byte length, exposes
  `ReadByte/WriteByte/Slice`-style accessors
- `class WacsHostFault : Exception` — binding-side traps; surfaced as wasm
  runtime errors

Independent versioning (`WACS.HostBindings.Abstractions` 0.1.0). Ships as a
NuGet package.

### Phase 3 — WASI Preview 1 ExecContext-free entry points (~2–3 days, the heavy lift)

For each of the 47 WASI Preview 1 functions, add a static overload that takes
`WacsHostMemory mem` + per-instance `State state` + the wasm-typed args,
returning `ErrNo` (or void). The existing IBindable instance methods become
thin wrappers:

```csharp
// before:
public ErrNo FdWrite(ExecContext ctx, fd fd, ptr iovsPtr, size iovsLen, ptr nwrittenPtr) {
    var mem = ctx.DefaultMemory;
    /* logic */
}

// after — IBindable wrapper (interpreter path unchanged):
public ErrNo FdWrite(ExecContext ctx, fd fd, ptr iovsPtr, size iovsLen, ptr nwrittenPtr)
    => FdWriteCore(new WacsHostMemory(ctx.DefaultMemory.Data, ctx.DefaultMemory.Length),
                   _state, fd, iovsPtr, iovsLen, nwrittenPtr);

// new — annotated static (AOT path):
[WacsImport("wasi_snapshot_preview1", "fd_write")]
public static ErrNo FdWriteCore(WacsHostMemory mem, State state,
                                fd fd, ptr iovsPtr, size iovsLen, ptr nwrittenPtr) {
    /* logic, parametric on (mem, state) */
}
```

The `State` parameter carries per-instance configuration (preopens, args, env,
fd table). Same `State` object the interpreter uses.

**Verification:** `Wacs.WASI.Preview1.Test` (43/72 wasi-testsuite fixtures
continue passing; no regressions).

### Phase 4 — `WACS.HostBindings.SourceGen` package (~1.5 days)

New netstandard2.0 Roslyn analyzer/source-gen project, modeled on the existing
`Wacs.Compilation` source generator (same csproj shape).

Inputs (from the consumer's compilation):

- A `[assembly: WacsTranspiledImports(typeof(IImports))]` attribute that the
  **transpiler will start emitting** on saved .dll's (small change to
  `InterfaceGenerator`). Identifies which referenced assembly's `IImports`
  interface needs adapting.
- All `[WacsImport]`-annotated static methods discoverable via the consumer's
  compilation references.

Output: a partial class `GeneratedHostImports : IImports` in the consumer's
compilation, with one method per `IImports` member, each body either:

- A direct call to the matching `[WacsImport]` static, OR
- `throw new WacsHostFault("no host binding registered for ...")` if no match

Diagnostics:

- `WACS001` (error): unmatched import
- `WACS002` (error): signature mismatch
- `WACS003` (error): ambiguous binding (multiple matches across packages)
- `WACS004` (info): matched binding (verbose mode)

The generator also emits a constructor on `GeneratedHostImports` that accepts
whatever shared-state arguments the matched bindings need (for WASI: a
`Wacs.WASI.Preview1.State`).

**Verification:** unit tests in `Wacs.HostBindings.SourceGen.Test` that feed
the generator a synthetic IImports + a synthetic binding class and assert the
emitted source compiles.

### Phase 5 — `wacs aot --wasi` wiring (~0.5 day)

- `AotOptions`: add `--wasi`, `--wasip2`, `--bind <path>` (mirror `wacs build`).
- `AotHandler`: when `--wasi` is set:
  - Skip the existing `--emit-main` path (which can't handle imports today)
  - Generated csproj adds `<PackageReference Include="WACS.WASI.Preview1" />`
    + `<PackageReference Include="WACS.HostBindings.SourceGen" />` (or
    `<ProjectReference>` when running from a source checkout)
  - Generated `Program.cs` does:

    ```csharp
    var state = new Wacs.WASI.Preview1.State(WasiConfiguration.Default(args));
    var module = new MyTranspiledApp.Module.Module(new GeneratedHostImports(state));
    return module._start();
    ```

  - The transpiler's `InterfaceGenerator` emits the
    `[assembly: WacsTranspiledImports]` attribute (small change — Phase 4
    dependency).

**Verification:** end-to-end `wacs aot hello.wasm -o hello --wasi` →
`./hello` prints "hello world" and exits 0.

### Phase 6 — Same treatment for `Wacs.WASI.Preview2` (~1 day)

Mirror Phase 3+4 for Preview 2's WIT-defined surface. The Component Model
already has typed C# interfaces per WIT package, so this is mostly
attribute-annotation rather than a full refactor. `wacs aot --wasip2` follows.

### Phase 7 — Docs + deprecation (~0.5 day)

- `docs/MIGRATION_WASIp1_to_WASI.md`: 1-page migration guide
- README updates: replace `WACS.WASIp1` references with `WACS.WASI.Preview1`
- NuGet `WACS.WASIp1` package metadata gets `<PackageDeprecationReasons>`
  (deprecation propagates to `dotnet add package` warnings)
- Update `docs/COLDSTART.md` "wacs aot" section to reflect WASI support

## Migration story (zero-friction)

For an existing embedder of `WACS.WASIp1`:

- **Update** the package reference and using lines (mechanical sed —
  see `docs/MIGRATION_WASIp1_to_WASI.md` shipped in Phase 7)
- The deprecated `WACS.WASIp1` metapackage continues to restore
  (transitively pulls in `WACS.WASI.Preview1`), but consumer code must
  swap `using Wacs.WASIp1;` for `using Wacs.WASI.Preview1;`. No API
  surface change.

For a new embedder targeting NativeAOT:

- Reference `WACS.WASI.Preview1` + `WACS.HostBindings.SourceGen`
- Construct `new GeneratedHostImports(state)` and pass to the transpiled Module
- Or use `wacs aot --wasi` and don't think about it

## Risks & open questions

1. ~~**Lokad.ILPack TypeForwardedTo support**~~ — moot: TypeForwardedTo
   doesn't bridge namespace renames in any framework, so we don't use it.
   The shim is a deprecated metapackage instead. (Discovered Phase 1 day 1.)
2. **Source-gen ergonomics for `State` initialization** — the generator needs
   to know how to construct shared state objects per binding package. Initial
   design: each binding package defines a
   `[WacsHostState] public sealed class State { public State(WasiConfiguration cfg) {…} }`,
   generator wires the consumer's ctor to accept all such states. Open: what
   if two packages need conflicting state? Defer; warn and let the embedder
   hand-construct in that case.
3. **`Wacs.WASI.Preview1.State` constructor arg** — in Phase 3, we add
   `State state` as a per-call arg. If `State` is internal, callers (the
   source gen) need access. Make it public or add a `[InternalsVisibleTo]`
   for the source gen + tests.
4. **Diagnostic UX** — Roslyn diagnostics need to be specific enough that an
   embedder can fix mismatches in their IDE without running the CLI. Worth
   prototyping early in Phase 4.
5. **Estimated sprint length: 6–9 working days.** Probably worth committing
   per phase and reviewing between Phase 3 and Phase 4 — the WASI refactor's
   surface area is large enough that mid-sprint course-correction may be
   needed.

## Phase ordering rationale

`Rename → Abstractions → WASI refactor → Source gen → wacs aot wiring →
Preview 2 → Docs`. The rename comes first because everything else lives in
the new namespace. Abstractions before refactor because the refactor uses
`WacsHostMemory`. Source gen before CLI wiring because the CLI consumes its
output. Preview 2 last because it's the biggest pattern-multiplier (we want
the Preview 1 refactor + source gen settled before applying to a second
package).
